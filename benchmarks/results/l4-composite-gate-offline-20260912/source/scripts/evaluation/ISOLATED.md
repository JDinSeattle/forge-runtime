# One isolated DeepSeek evaluation deployment

This launcher is operator tooling for the existing `lr20260912_a` pool and the selected `deepseek/deepseek-v4-flash` eval-v2 batch. It has not yet started a host service, contacted PostgreSQL, read the model key, or made a paid call. Its tests use real private SQLite files and explicit offline process/PG/Docker fixtures. Independent review and actual preflight precede host execution.

Use an independently created evaluation directory `E` under the existing scope's `evaluation/`. The ordinary checkout owner prepares `E/source` as a clean checkout of the reviewed integrated revision, builds all seven binaries from that checkout, creates the existing candidate bundle and runs the independently reviewed provisioner. Preserve every lifecycle input, binary, journal, owner marker, image and prior failure.

The layout is fixed:

```text
lr20260912_a/
  runtime/                 existing journal, key, engine, artifacts, authority configs
  pool-root/               existing four mounted ext4 images, unchanged
  evidence/sigterm-02/      completed actual E50
  evidence/logs-01-cleanup/ material Stop/Snapshot/Release proof for retained logs01
  evidence/logs-02/         retained before-runner failure, never overwritten
  evidence/logs-02-before-runner-observation/ pinned read-only no-work proof
  evidence/logs-03/         original failed aggregate, five actual cases passed
  evidence/logs-03-recovery/ explicit old L4 cleanup, required by composite gate
  evidence/logs-l4-01/      separate targeted L4 + health, required by composite gate
  evaluation/
    deepseek-flash-2usd.entitlement.json  created exclusively at first launch
    <one-evaluation>/
      source/              clean integrated source checkout
      bin/                 all binaries below, same clean VCS revision
      candidate/           prepare.py output with sources under E/source
      private/             provisioner output; DSN files remain private
      deployment.json      collector's existing exact v1 descriptor
      launch.json          nonsecret closed identity generated by seal
      evidence/
        preflight-01.json  explicit new read-only preflight report
        launch/            one exclusively created host/child execution record
        eval-01/           sole collector batch, never auto-replaced
```

Build from `E/source`; outputs must be new files in `E/bin`. Existing lifecycle executables are not overwritten.

```sh
go build -o "$E/bin/forge" ./cmd/forge
go build -o "$E/bin/forge-api" ./cmd/forge-api
go build -o "$E/bin/forge-worker" ./cmd/forge-worker
go build -o "$E/bin/forge-runner" ./cmd/forge-runner
go build -o "$E/bin/forge-admin" ./cmd/forge-admin
go build -o "$E/bin/eval-provision" ./scripts/evaluation/provision
go build -o "$E/bin/eval-preflight" ./scripts/evaluation/preflight
```

The binary guard reads Go build information and requires the expected main package, Linux/amd64, the same full VCS revision, and `vcs.modified=false`. It records binary SHA256 and Go version. The launcher recomputes tracked Go, SQL, Python, shell, JSON/config, module and corpus text identities from the clean checkout. Compiled artifacts are built before provisioning so the original two-hour launch/token deadlines are useful; no deadline or quota is renewed by the launcher.

After candidate/provisioning are complete, invoke only the tools in that frozen `E/source`:

```sh
python3 -I -B "$E/source/scripts/evaluation/isolated.py" seal --evaluation-root "$E"
python3 -I -B "$E/source/scripts/evaluation/isolated.py" preflight \
  --evaluation-root "$E" --report "$E/evidence/preflight-01.json"
python3 -I -B "$E/source/scripts/evaluation/isolated.py" launch --evaluation-root "$E"
```

`seal` creates only `deployment.json` and `launch.json`. They contain no credential bytes or credential digest. It requires actual E50 and the selected complete log evidence contract below, the same journal UUID, logs01 material cleanup, unchanged historical runner inputs, and exact four-case corpus/profile/grader reconstruction. The candidate hash alone cannot authorize a different grader command, image, source, fake provider, fallback, log policy, capacity or runner authority.

`preflight` opens the existing `.sigterm-control.lock` without creating/rebinding it. It rejects missing or stale UDS paths rather than unlinking them. It checks prior recorded processes and dedicated unit cgroups, a free API port, all four mounts through production `sandbox.VerifyVolume`, unchanged owner-marker bytes and persisted slot specifications, SQLite v5 UUID and sole artifact registry, zero unsettled operations/workspaces/leases, and durable removal of every strict-log container. Docker queries select only exact operation labels from the journal and require absence; they never remove containers or pull images. The pinned Python and Go images must already exist.

The five retained fixture schemas (six under the explicit composite contract below) are read through their private descriptors and bound to the original public role/schema/run records. Live queries are read-only and fully schema-qualified. Completed fixtures must have zero active capacity, requests, unresolved effects, reservations or cleanup. The first failed before-runner run is deliberately different: it must still match its original `cancel_requested`, version2, epoch0 snapshot with no work. Its DSN is never given to the new worker. Prior namespace OIDs were not captured uniformly by the historical fixtures; the guard binds their names, roles and recorded runs and does not invent an older OID observation. The new evaluation schema is bound to its provisioned OID, must contain zero projects/runs/attempts/effects/artifacts, and must retain its original zero-spend quota generation/window. Both database and local clocks must still be within the original deadlines. The collector's actual audit-role preflight runs before any process is started.

The administrator DSN is read only from the existing private `var/local/review-database.env`. API/worker/audit DSNs are parsed with `shlex` without executing a shell; only the provisioner's exact options and schema/role are accepted. `client.env` follows its three plain-literal values contract. The model key's fixed path is the main checkout's `var/evaluation/deepseek.env`. Preflight checks metadata only. The mapped child reads that file only immediately before launching the worker; its sole key is `DEEPSEEK_API_KEY`. It is never put in argv, unit properties, descriptors, logs, a copied file, or a hash.

`launch` creates a unique delegated transient user service and a new RootlessKit state directory. `/usr/bin/env -i` clears the service manager environment before RootlessKit starts. The mapped child requires UID0→host1000 plus full subordinate UID/GID maps and the recorded service cgroup. It holds the same lifecycle control lock throughout the deployment and repeats live preflight. It starts runner→API→one worker with minimal per-role environments, records PID/start ticks/executable hash/full argv, verifies the actual runner UDS peer, authenticates with the implemented GET of an absent run (403 without token, 404 with the exact token) and rechecks the empty private schema. The collector receives only its audit DSN; runner and API receive no provider key.

The collector is invoked once with `--execute`, one fixed `eval-01` directory, four 500,000-microUSD task allocations, and 2,000,000 microUSD total. An exclusive persistent entitlement binds this directory and registration even after a failed startup. There is no second execute, automatic fallback, approval, run retry, provider retry or new batch. Unknown submission and usage remain accounted for by the collector. A request alias is not a pinned server version; checksum-verified native response artifacts remain evidence of the returned model.

Normal closure requires all four exact tenant/run IDs terminal, no unknown fee reserve, no budget violation, and no active/unresolved execution authority. The launcher then calls production `forge-admin workspace-gc` for only those IDs. That path seals/publishes a snapshot before release. It never calls global artifact GC on the reused artifact root. Finally API receives SIGTERM and drains/exits; a new TCP connection must explicitly return `ECONNREFUSED`; worker receives SIGTERM and exits; runner receives SIGTERM and exits. Each signal/exit is bound to the original PID, start ticks, executable hash and argv. Post-shutdown PG/SQLite/mount/container checks must show no remaining work; the exact new unit must be gone or inactive with its cgroup empty. This is an ordered idle deployment shutdown; it composes with the separately recorded busy E45/E47/E50 evidence and is not a claim that all three were busy in one experiment.

On failure the collector intents, fees, schemas, unknown containers/workspaces and all logs remain. The launcher stops only its own API/worker/runner processes in that order, never sends business Cancel or Docker kill/remove as a fallback, and records unconfirmed shutdown rather than claiming success. The service has its own finite runtime/stop bounds. If it times out or the supervisor exits unexpectedly, inspect the exact recorded unit and process identities; the launcher cannot authorize erasing unknown work or creating another paid batch.

`--collect` remains the existing collector's evidence-only operation on the same `deployment.json`, `candidate`, `client.env` and `eval-01` while its exact services are available. This launcher does not restart an interrupted deployment or recreate missing state automatically. Preserve partial evidence and diagnose its recorded phase before any separate recovery action.

## Explicit five-case plus targeted L4 composition

The separate `logs-l4-continuation.json` seal selects the new contract. Its absence leaves the original all-six gate intact; a failed or incomplete composite never falls back to another evidence path. The current logs03 aggregate remains `passed:false`. Recovery is an explicit cancellation/reconciliation and release of the old L4, **not** passing ENOSPC evidence. No actual recovery or targeted success is manufactured by this tooling.

The seal has purpose `strict-logs-targeted-l4-v1`, the exact old `recovered_run_id`, the pinned `failed_manifest_sha256` and `observation_manifest_sha256`, plus actual `recovery_manifest_sha256` and `acceptance_sha256`. The latter binds `acceptance-logs-l4-01.json`. Its producer remains the independently reviewed lifecycle workflow. This consumer does not create that seal or change any historical acceptance.

The closed input set includes the original 602-member logs03 manifest, six-member retained observation, three-member final SQL-lease observation, the complete recovery archive, and the complete targeted archive. Exact generated filenames and artifact IDs are admitted before hashing; `database.json`, environment files, keys, symlinks, traversal and arbitrary runtime files are rejected. The four exact owner markers must still contain the original journal path. Recovery and targeted before/after inputs must match; targeted input identity must include the entire prior failure and recovery history. All returned nonsecret members, including the manifest hashes, enter the existing evaluation launch seal.

The targeted consumer checks all three physical pressure stages (1 MiB, 4096 bytes, one byte) with actual ENOSPC/sync observations and zero remaining Bavail. It binds pressure to the original workspace sibling and spool device, the unchanged operation request and container across before/failure/recovered/final journal snapshots, the early nonzero/non-OOM container stop inside the paused-worker window and original request deadline, and the retained two-stream FLG prefix with CRCs. Receipt bytes must agree with the RPC result and artifact hashes; PG effect/READY rows and authenticated HTTP bytes must reference that original log. Closure must have zero capacity counters and released cleanup. A separate successful real health operation must have its own receipt/container and Stop/Snapshot/Release records. No summary boolean can replace these files.

The new `runtime/strict-logs-l4-private-01/database.json` is used only for an exact read-only observer. Its role, schema and single run must match the targeted public fixture. Original logs03 is additionally bound to namespace OID 852843, its original L1 and cancelled L4 post-cleanup snapshots, original deadline, execution/publication counts, and zero unsettled resources. The original SQL heartbeat lease and older reducer snapshot remain separately preserved in their immutable observations. The first unstarted SIGTERM run remains `cancel_requested`; the second unstarted logs attempt remains `queued`. No old descriptor is routed to the evaluation worker.

Before starting the deployment, the observer compares a grant-stripped, read-only SQLite transaction to the targeted final journal, including every row of its seven known tables. It checks recorded recovery runner and targeted worker/runner process identities have exited. These results and the composite source report appear under `prior_processes.log_evidence_composition` and `prior_processes.targeted_journal_baseline` in the existing preflight report.

The source report preserves original logs03 revision `bdff9b1b511ae1c38327b8441ac973bb4db262e2` and each newer recovery/targeted binary identity. Production Git objects under `internal/`, `cmd/`, `db/`, `proto/` (including generated RPC Go), `go.mod` and `go.sum` must be identical. The runner/worker executable build information must report the same clean revision as its exact frozen directory; the test executable is retained by its acceptance SHA. Tooling, fixture and documentation revisions may differ; this is not a claim that the original five cases ran a newer executable.

Offline composite tests are `test_composite.py`, alongside the existing launcher and collector tests. They exercise real temporary SQLite read-only comparisons, binary FLG/receipt bytes, synthetic public PG/HTTP/material records, and malformed inputs. They do not execute the production runner, PostgreSQL, Docker, a mount, systemd or a model. The actual gate stays closed until all named material outputs exist and pass these checks. The one-time $2 entitlement and four $0.50 allocations are unchanged.
