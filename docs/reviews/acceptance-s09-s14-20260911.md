# Sections 9–14 acceptance scope review, 2026-09-11

This independent read-only review compared all **31 then-I rows** in sections
9–14 of the implementation map with the original
[SDE specification](../spec/SDE_IMPLEMENTATION_PLAN.md), current implementation,
test sources and retained E01–E27 evidence. It recommends **23 promotions** and

run a provider, execute another container fault, or turn a source inspection into
a new test result. New input-snapshot and dependency-deadline changes are reviewed

## Interpretation and evidence limits

- Section 10 explicitly requires pinned native adapters and **contract tests**.
  It does not require a live provider call as an additional adapter-level gate.
  The separate section 17 explicit-budget smoke evaluation and P07 remain open;
  E02/E26 native HTTP fixtures are not paid inference or model-quality results.
- Section 10 requires safe closed-boundary provider switching, but does not
  prescribe automatic routing. Missing automatic fallback alone must not create
  an extra requirement. The current implementation has no actual same-run
  cross-provider handoff path either; that smaller missing behavior is why
  S10.3 and the switching clause of S10.8 remain open here.
- E18 is actual runner/Docker/SQLite/filesystem evidence, with application SQL
  ledgers explicitly N/A. E21/E25/E27 provide their own application-level
  evidence. E27 F11/F12 begin after an original command's durable success while
  PostgreSQL still says in flight; they are not active-writer interruptions.
- E27 ran production `224a6b6` plus its frozen harness, excluding the concurrent
  retry/deadline changes. Its PostgreSQL outage responses really were
  `500 / internal / retryable=false`. Neither source changes nor this review
  relabel that observation as a 503 response or a successful retry hint.
- Saved phase exports are sequential table reads. Auditing bindings, receipts,
  hashes and sequences does not make them globally atomic snapshots. Models and
  prices in E06/E12/E21/E25/E27 are deterministic fixtures. E20 retains its exact
  200-client/20-run/5 Hz/1 KiB parameters, explicit slow receive-window constraint,
  and production server defaults.
- “Full matrix”, “every interleaving”, “one scenario exercises every event”, and
  a long fuzz campaign are not added to individual implementation rows where
  the original specification asks for a concrete protocol and necessary checks.
  Existing mandatory fault/performance rows retain their own gates.

## Two concrete open-path checks

S14.2 is not merely a missing exhaustive test. In the retained E27 F11 HTTP
records, the database proxy cut produces actual connection errors and the public
response remains `internal` with `retryable=false`. Adding the current deadline
branch fixes a different case. A minimal follow-up should classify a real failed
database connection as the documented dependency error, preserve request IDs,
and avoid converting domain validation/conflict errors into retryable failures.
No new fault campaign is required to demonstrate that distinction.

For S14.5, a minimal controlled reproduction is: obtain a valid developer token;
hold the tenant-runtime lock; start an exact approval request so authentication
has completed and `Decide` waits; downgrade/delete that principal's membership
through the fixture administrator; release the lock. Current `Decide` never
reads memberships and still uses the prior developer identity. This is a
source-traced reproducible path, **not a newly executed race result**. Rechecking
the current role at the decision transaction's authorization point closes the
specific requirement; the choice of a short membership lock must follow a
consistent ordering with administrative updates.

## Ordinary input-snapshot change

The new `persistence/input.go` and ordinary `Store.Submit` branch have no
identified P1/P2 issue in this bounded review:

- A new ordinary submission reads source/profile from the same tenant/project
  under `FOR SHARE` inside the existing bounded transaction. The versioned JSON
  stores project, task, base, source and profile; run configuration remains in
  its separate frozen column.
- Snapshot creation occurs only after the new idempotency-key insertion wins.
  Same-key replay returns the original run without generating different input
  bytes. No new wire field or derived snapshot bytes alter the old request hash.
- A retry validates the terminal parent and identical tenant/project/task/base,
  then copies its exact stored input bytes. Empty legacy values are preserved,
  not misrepresented as reconstructed historical snapshots. Fresh execution
  state and costs remain separate.
- The added work is a short project SELECT plus local JSON serialization. There
  is no external I/O while holding the transaction. The currently exposed API
  has no project source/profile mutation route; this review does not assume an
  operator can rewrite those bindings concurrently without a separate policy.
- The updated real-PG review test reads and checks the admission-generated
  nonempty JSON instead of manually updating `input_snapshot`. Its execution
  status must be recorded by the root's actual test log; source inspection alone
  is not a passing integration result.

The preceding S07.4 deadline review found no reachable P1/P2. The retained
repeat log `/tmp/forge-dependency-deadlines-integration-repeat-20260911.log`
records the six new PG/TCP/Driver tests passing after correcting asynchronous
pgx pool-release observation and restoring the test's production 30-second
execution lease. The initial failed log and original test sources remain in
`benchmarks/results/dependency-deadlines-20260911`. That test-only correction did
not extend production authority or substitute a new transaction deadline.

This review does not cover the concurrently added priority field/schema 9 or
claim that a new whole-tree build, race run, clean clone or hosted CI has passed.
